## AI Diary

This session taught me what "working in production" really means versus "working in theory." Every single fix I made revealed another assumption that was wrong. I assumed the login page had Turnstile — it didn't. I assumed the page redirected to passport after registration — it goes to portal/member first. I assumed 60 seconds was enough for OTP — sometimes it's not. I assumed a 15-second timer would be enough for the last verify before Discord — it wasn't.

The most humbling moment was the `portal-member` stage discovery. The redirect chain `register → portal/member → passport/login` seems obvious in retrospect, but the "other" stage handler was silently intercepting the flow, navigating back to register before the natural redirect could happen. Only 1 out of 3 accounts was getting verified because of a race condition between the 10-second "other" handler and the browser's redirect timing.

Gabbzaa's approach of watching the extension run live and sending screenshots was invaluable. Each screenshot was a precise diagnosis — "here's the log, here's the state, fix it." The constraint of "แก้ไข ไม่ใช่ลบทำใหม่" (fix, don't delete and redo) forced me to understand every interaction between CSUI lifecycle, background handlers, and page navigation. The Chrome extension's content script being destroyed on navigation is the fundamental challenge — you can't trust any code after a page change to execute.

The OTP fix was a good lesson too. Manual fallback for a temp email is nonsensical — the user has no access to the Makeloops inbox. Auto-retry with resend is the only correct approach.

## Honest Feedback

**Friction Point 1: Cascading assumptions.** I built the verify-login flow assuming certain page behaviors without testing them first. The Turnstile assumption, the redirect chain assumption, and the timing assumption all compounded into a flow that looked correct on paper but failed in practice. I should have traced the actual browser navigation path before writing handler code.

**Friction Point 2: Timer-based coordination is fragile.** Using `setTimeout(15000)` in batch-control to "wait for verify to finish" was a hack. The right pattern — which we eventually implemented — is to have the actual completing action (verify-login) trigger the next step (Discord send). Event-driven, not timer-driven.

**Friction Point 3: Stage detection gaps.** The original 5-stage system missed `portal-member` entirely. When building a multi-page automation flow, every URL the browser can land on needs a handler. The "other" catch-all should be truly passive (just log), not take action that interferes with the intended flow.

## Lessons Learned

1. **CSUI lifecycle is the #1 constraint** — Any code after a page navigation may not execute. Save critical state BEFORE navigation triggers. Background handlers survive; content scripts don't.

2. **Trace the actual redirect chain** — Don't assume: `register → portal/member?success → passport/login`. Each intermediate page needs its own stage handler.

3. **Auto-retry > manual fallback** — For automated flows, manual intervention is a design flaw. OTP timeout should resend and retry, not ask the user.

4. **Event-driven > timer-driven** — Discord sends after verify-login completes, not after an arbitrary delay. The completing action triggers the next step.

5. **Check what's actually on the page** — Login page has no Turnstile. Don't assume features exist; detect them.
